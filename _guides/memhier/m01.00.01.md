## Introduction

You're probably in Dr. Peterson, Dr. Marz, or Dr. Jantz's class looking for a **more-detailed writeup** for building this simulator.

In this guide, I explain the memory hierarchy, how each reference flows through it, and how to build the simulator incrementally by modeling each layer and tracking the right statistics.

***Note:** I implemented this simulator in C in roughly 700 lines of code. You may end up writing more than this, if you are creating helpers, functions for verifying behavior, etc. Start the assignment early!*

You can use [this JS simulator](/apps/memhier) to step through each access.

## The Big Picture

A real CPU does not talk directly to disk. Every memory reference goes through two separate jobs, one after the other:

1. **Translation:** turn the address into a physical page number.
2. **Data access:** find the data at that physical address.

Each job has its own chain of structures:

```
Translation (virtual addresses only)        Data access (always)

  TLB                                        L1 data cache (DC)
   | miss                                     | miss
   v                                          v
  Page table                                 L2 cache (if enabled)
   | miss (page fault)                        | miss
   v                                          v
  Disk                                       Main memory
```

Keep these two chains separate in your head, because the statistics depend on it:

- **Disk references only come from the translation side.** A page fault reads the page from disk, and if the page being thrown out was written to, it is written back to disk too. A cache miss *never* goes to disk.
- **Main memory references only come from the data side**: L2 misses (or DC misses when L2 is off), dirty lines written back from L2 (or from the DC when L2 is off), and writes that a write-through L2 passes on to memory.

## Which Layers Can Be Turned Off

The config file has three switches at the bottom, but they are not independent:

| Layer | Can it be off? |
| --- | --- |
| Data cache (DC) | No, it is always on. |
| L2 cache | Yes, `L2 cache: n`. |
| Page table | Only exists when `Virtual addresses: y`. |
| TLB | Only allowed when virtual addresses are on. `TLB: y` with `Virtual addresses: n` is a config error. |
{: .pretty }

When virtual addresses are off, the trace address *is* the physical address and there is no translation at all. The page number is still checked first against the number of virtual pages (reported as "virtual address … is too large"), and then against the number of physical pages.

## What One Reference Does

For every trace line, in this order:

1. Read the access type (`R` or `W`) and the hex address.
2. Split the address into a page number and a page offset.
3. **Translate** (only if virtual addresses are on):
   - Look in the TLB. On a hit you have the physical page number.
   - On a TLB miss, or if the TLB is off, look in the page table. That counts as a page table reference.
   - On a page table miss (a **page fault**), count a disk reference, pick a free physical page or the least recently used one, and update the page table and TLB.
4. If this is a write, mark the page dirty in the page table.
5. Build the physical address from the physical page number and the same offset.
6. **Look up the DC** with the physical address.
7. **On a DC miss**, look up L2 if it is enabled. On an L2 miss (or a DC miss with no L2), count a main memory reference.
8. Update hits, misses, LRU ages and dirty bits as you go.

A page fault is more than a miss. When a physical page is replaced, everything that still points at it has to go:

- DC and L2 lines from that page are invalidated (dirty ones are written back first),
- TLB entries pointing at that page are invalidated,
- the old page table entry is marked invalid, and if that page was dirty, it costs one more disk reference.

Students skip this part more than any other, and it is where a lot of mismatched statistics come from.

## What the Input Looks Like

The simulator reads its settings from a file named `trace.config`:

```
Data TLB configuration
Number of sets: 2
Set size: 1

Page Table configuration
Number of virtual pages: 64
Number of physical pages: 4
Page size: 256

Data Cache configuration
Number of sets: 4
Set size: 1
Line size: 16
Write through/no write allocate: n

L2 Cache configuration
Number of sets: 16
Set size: 4
Line size: 32
Write through/no write allocate: n

Virtual addresses: y
TLB: y
L2 cache: y
```

The numbers of sets and pages, the page size and the line sizes must all be powers of two (set sizes don't have to be). `Write through/no write allocate: n` means the cache is write-back/write-allocate.

The trace comes in on stdin, one reference per line, as `R` or `W`, a colon, and a hex address:

```
R:c84
R:c8c
W:c84
R:1a3c
R:2f00
R:3b48
R:0910
```

## A Worked Example

Here is what a correct simulator prints for the config and trace above (after the config summary):

```
Virtual  Virt.  Page TLB    TLB TLB  PT   Phys        DC  DC          L2  L2
Address  Page # Off  Tag    Ind Res. Res. Pg # DC Tag Ind Res. L2 Tag Ind Res.
-------- ------ ---- ------ --- ---- ---- ---- ------ --- ---- ------ --- ----
00000c84      c   84      6   0 miss miss    0      2   0 miss      0   4 miss
00000c8c      c   8c      6   0 hit          0      2   0 hit
00000c84      c   84      6   0 hit          0      2   0 hit
00001a3c     1a   3c      d   0 miss miss    1      4   3 miss      0   9 miss
00002f00     2f    0     17   1 miss miss    2      8   0 miss      1   0 miss
00003b48     3b   48     1d   1 miss miss    3      d   0 miss      1   a miss
00000910      9   10      4   1 miss miss    0      0   1 miss      0   0 miss
```

### Row 1, step by step: `R:c84`

**Split the address.** Pages are 256 bytes, so the low 8 bits are the offset.

- Offset = `0xc84 & 0xff` = `0x84`
- Virtual page = `0xc84 >> 8` = `0xc`

**TLB.** There are 2 sets, so the TLB index is `0xc % 2 = 0` and the tag is `0xc / 2 = 6`. The TLB is empty, so it misses.

**Page table.** Virtual page `0xc` isn't loaded yet, so this is a page fault. That's one page table reference and one disk reference. Physical page 0 is free, so the page goes there.

**Physical address.** Same offset, new page number: `(0 << 8) | 0x84` = `0x084`.

**DC.** Lines are 16 bytes and there are 4 sets.

- Block = `0x084 >> 4` = `8`
- Index = `8 % 4` = `0`
- Tag = `8 / 4` = `2`

The DC is empty, so it misses.

**L2.** Lines are 32 bytes and there are 16 sets.

- Block = `0x084 >> 5` = `4`
- Index = `4 % 16` = `4`
- Tag = `4 / 16` = `0`

It misses, so the data comes from main memory: one memory reference.

Notice that the caches index the **physical** address `0x084`, not the trace address `0xc84`.

### Rows 2 and 3: hits

`R:c8c` is on the same page, so the TLB hits. A TLB hit means **no page table reference**. It is also in the same 16-byte DC line as `0xc84` (block 8 again), so the DC hits. On a DC hit, L2 is never consulted, which is why the L2 columns are blank.

`W:c84` hits in the TLB and DC too. Because the DC is write-back, the line is only marked **dirty**; nothing goes to L2 or memory yet. The page table entry for page `0xc` is also marked dirty, which matters later.

### Row 5: a write-back you can't see in the table

`R:2f00` lands on physical page 2, physical address `0x200`, DC block `0x20`, which is DC index 0. Index 0 already holds the dirty line from row 3 (tag 2), so that line is evicted and **written back to L2**. That write-back hits in L2 (L2 still has block 4 from row 1) and makes that L2 line dirty.

None of this is visible in the printed row, which just shows the new DC miss and L2 miss. The write-back does show up in the statistics: it's the one L2 hit in the whole run. Your `trace.log` should say:

```
writing back DC line with tag 2 and index 0 to L2 cache
```

### Row 7: a page replacement

By row 6, all 4 physical pages are in use. `R:0910` faults on virtual page 9, so a page has to go. The least recently used physical page is page 0, which holds virtual page `0xc`.

Here is everything that happens before the new page can be loaded:

1. Virtual page `0xc` was written in row 3, so it is dirty. Writing it back to disk is a **second** disk reference for this one trace line.
2. Its page table entry is marked invalid.
3. Any DC lines from physical page 0 are invalidated. There are none left, since row 5 already evicted it.
4. Any L2 lines from physical page 0 are invalidated. L2 tag 0, index 4 is still there and **dirty** (from row 5's write-back), so it is written to main memory first: one more memory reference.
5. Any TLB entries pointing at physical page 0 are invalidated. The one for page `0xc` was already replaced in row 4, so there are none.

Then page 9 is loaded into physical page 0, and the lookup continues as normal.

### The statistics

The counts from the end of the run (hit ratios and read/write totals left out):

```
dtlb hits        : 2
dtlb misses      : 5
pt hits          : 0
pt faults        : 5
dc hits          : 2
dc misses        : 5
L2 hits          : 1
L2 misses        : 5
main memory refs : 6
page table refs  : 5
disk refs        : 6
```

Every number can be traced back to a row:

- **Page table refs 5:** one per TLB miss. The two TLB hits never touch the page table.
- **Disk refs 6:** 5 page faults, plus 1 for writing dirty page `0xc` back to disk in row 7.
- **L2 hits 1:** the write-back in row 5, even though no row prints an L2 hit.
- **Main memory refs 6:** 5 L2 misses, plus 1 for the dirty L2 line flushed in row 7.

If your simulator gets this example right, including the two "extra" references, you have most of the hard parts working.

## Where to Start Coding

Before you touch the main loop, get the boring plumbing working first:

- Parse `trace.config` and load every parameter into named variables. Print the config summary as you parse, since the assignment expects it before the first trace line runs anyway.
- Precompute the shift amounts you will reuse on every reference: `lg2(page_size)`, `lg2(dc_line_size)` and `lg2(l2_line_size)`. Do this once at startup, not inside the loop.
- Get a bare loop reading `access_type` and `raw_address` from stdin and printing them back before you wire up any cache logic at all.

Once that skeleton runs cleanly, module 2 walks through how to structure the translation and cache stages around it.

## Why the Layers Matter to Code

The simulator is not a single lookup table.

- The TLB, DC and L2 each have their own sets, with valid bits, tags, dirty bits and LRU ages. The page table has a valid bit, a dirty bit and a physical page number per virtual page.
- The TLB, DC and L2 all work the same way: a set-associative lookup with LRU replacement. That means one lookup function can serve all three.
- Writes behave differently from reads, and differently again depending on each cache's write policy.

So the best implementation strategy is:

- Keep each layer's state separate
- Write one reusable set-associative lookup and call it for the TLB, DC and L2
- Make the main loop drive the stages in order: translation first, then data access

## Practical Mental Model

There are only two kinds of address:

- **Virtual address:** what the trace gives you when `Virtual addresses: y`. Only the TLB and page table use it.
- **Physical address:** what the caches always use. When `Virtual addresses: n`, the trace address already is the physical address.

Either way, the page offset never changes during translation; only the page number does.

## Programming Tips

- Get the config parsing and header printout exactly right before writing any cache logic. The output format is graded line by line, so a misparsed config file will throw off everything downstream.
- Store layer parameters as named variables (`page_size`, `num_dc_sets`, `dc_line_size`, ...) instead of re-reading a config struct everywhere.
- Write the `trace.log` messages (write-backs and invalidations) from the start. When your statistics don't match, the log is how you find out which reference went wrong.

## Common Mistakes

- Counting a disk reference on a cache miss (disk references only come from page faults and dirty pages being replaced)
- Counting a page table reference on a TLB hit
- Indexing the caches with the trace address instead of the physical address
- Forgetting the extra disk reference when the replaced page is dirty
- Forgetting to invalidate the replaced page's DC lines, L2 lines and TLB entries
- Treating L2 and L1 as independent when the assignment requires inclusion: when an L2 line is evicted, the DC lines inside it must go too
- Forgetting that a write behaves differently in write-through vs write-back

## What to Take Away

After this module, you should be able to answer:

- Which part of a reference can cause a disk reference, and which can cause a main memory reference?
- Why does a TLB hit skip the page table entirely?

- Why do the caches use the physical address and not the trace address?
